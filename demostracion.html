El caso de estudio

Una máquina de estados finitos que modela una puerta con control de acceso. Cuatro estados y cuatro eventos:

EstadoSignificado
CERRADOReposo, puerta asegurada
AUTORIZANDOCredencial recibida, validando
ABIERTOAcceso concedido
BLOQUEADOEstado terminal tras tres fallos consecutivos

El módulo es puro: no contiene hardware ni entrada/salida, de modo que sus pruebas pueden ejecutarse dentro del contenedor de Jenkins sin necesidad de una tarjeta física.

Por qué este ejemplo

El umbral de bloqueo está definido como una constante. Cambiar ese valor de 3 a 2 produce código que compila sin errores pero cuyo comportamiento ya no es el especificado.

Esa distinción entre «no compila» y «compila pero está mal» es el eje de la demostración.

Advertencia — sobre el token de GitHub

Desde 2021 GitHub no acepta contraseñas para operaciones de Git. Se requiere un token de acceso personal con el alcance repo habilitado. Un token fine-grained sin permiso de escritura produce un error 403 aunque la autenticación sea correcta.

El token equivale a una contraseña: no debe escribirse en archivos del repositorio ni en documentación. Si se expone, revocarlo de inmediato — borrarlo de un archivo no lo elimina del historial de Git.

FASE 1 Código fuente

Interfaz del módulo

src/puerta.h 
#ifndef PUERTA_H
#define PUERTA_H

#include <stdint.h>

#define MAX_INTENTOS 3u   /* bloqueo tras este numero de fallos */

typedef enum {
    EST_CERRADO = 0,
    EST_AUTORIZANDO,
    EST_ABIERTO,
    EST_BLOQUEADO
} estado_t;

typedef enum {
    EV_CREDENCIAL = 0,
    EV_OK,
    EV_FALLO,
    EV_TIEMPO
} evento_t;

typedef struct {
    estado_t estado;
    uint8_t  intentos;
} puerta_t;

void        puerta_init(puerta_t *p);
estado_t    puerta_evento(puerta_t *p, evento_t ev);
const char *puerta_nombre(estado_t e);

#endif /* PUERTA_H */

Implementación de la máquina de estados

src/puerta.c 
#include "puerta.h"
#include <stddef.h>

void puerta_init(puerta_t *p)
{
    if (p == NULL) {
        return;
    }
    p->estado   = EST_CERRADO;
    p->intentos = 0u;
}

estado_t puerta_evento(puerta_t *p, evento_t ev)
{
    if (p == NULL) {
        return EST_BLOQUEADO;   /* falla segura */
    }

    switch (p->estado) {

    case EST_CERRADO:
        if (ev == EV_CREDENCIAL) {
            p->estado = EST_AUTORIZANDO;
        }
        break;

    case EST_AUTORIZANDO:
        if (ev == EV_OK) {
            p->estado   = EST_ABIERTO;
            p->intentos = 0u;           /* exito: reinicia contador */
        } else if (ev == EV_FALLO) {
            p->intentos++;
            p->estado = (p->intentos >= MAX_INTENTOS)
                      ? EST_BLOQUEADO
                      : EST_CERRADO;
        }
        break;

    case EST_ABIERTO:
        if (ev == EV_TIEMPO) {
            p->estado = EST_CERRADO;    /* cierre automatico */
        }
        break;

    case EST_BLOQUEADO:
    default:
        /* Estado terminal: solo se sale reinicializando. */
        break;
    }

    return p->estado;
}
Nota — dos decisiones de diseño con intención didáctica

Un puntero nulo devuelve BLOQUEADO en lugar de abrir la puerta: falla segura.

Un acceso exitoso reinicia el contador de intentos, de modo que tres fallos separados por un acierto no bloquean el sistema.

Punto de verificación

El módulo debe compilar sin advertencias bajo -Wall -Wextra -Werror:

bash 
gcc -std=c11 -Wall -Wextra -Werror -Isrc -c src/puerta.c -o /tmp/p.o

El uso de -Werror convierte cualquier advertencia en error. Es la misma política que aplicará el pipeline.

La prueba clave del umbral

tests/test_puerta.c 
static void test_bloqueo_tras_tres_fallos(void)
{
    puerta_t p;
    unsigned i;
    puerta_init(&p);

    /* Dos fallos: vuelve a CERRADO, aun sin bloquear. */
    for (i = 0u; i < 2u; ++i) {
        puerta_evento(&p, EV_CREDENCIAL);
        MT_ASSERT_EQ(puerta_evento(&p, EV_FALLO), EST_CERRADO);
    }

    /* Tercer fallo: bloqueo. */
    puerta_evento(&p, EV_CREDENCIAL);
    MT_ASSERT_EQ(puerta_evento(&p, EV_FALLO), EST_BLOQUEADO);
}

FASE 3 El Makefile
Makefile · extracto 
APP      := control-acceso
VERSION  ?= 0.1.0
CC       ?= gcc
CFLAGS   := -std=c11 -Wall -Wextra -Werror -O2 -Isrc \
            -DAPP_VERSION=\"$(VERSION)\"

all:     # compila el ejecutable
test:    # compila y ejecuta pruebas; genera JUnit XML
package: # empaqueta el binario en un .tar.gz versionado
clean:   # borra todo lo generado
help:    # lista los objetivos disponibles
Regla de oro

El pipeline no contiene lógica de compilación: únicamente invoca objetivos de este Makefile. La consecuencia práctica es que cualquier participante puede ejecutar exactamente lo mismo en su máquina sin instalar Jenkins, y que un fallo del build se reproduce localmente sin depender del servidor.

La variable VERSION usa ?= para que el pipeline pueda sobrescribirla con el número de ejecución, ligando cada artefacto al build que lo produjo.

Nota — volumen nombrado, no bind mount

La documentación oficial desaconseja montar una carpeta del sistema anfitrión sobre /var/jenkins_home, porque el usuario jenkins dentro del contenedor opera con un identificador específico y esto produce conflictos de permisos. FASE 5 El pipeline
Jenkinsfile 
pipeline {                       // raiz de la sintaxis declarativa

    // AGENTE: donde se ejecuta el trabajo. "any" = cualquier nodo.
    // En produccion esto es mala practica: el build pesado debe ir
    // a un agente dedicado, no al controlador.
    agent any

    // OPCIONES: politicas operativas del pipeline completo.
    options {
        timestamps()                        // hora en cada linea
        timeout(time: 10, unit: "MINUTES")  // aborta build colgado
        buildDiscarder(logRotator(numToKeepStr: "10"))
        disableConcurrentBuilds()
    }

    // DISPARADORES: cierran el ciclo de integracion continua.
    // pollSCM consulta el repositorio cada 2 minutos y lanza una
    // ejecucion SOLO si detecta commits nuevos.
    //
    // La "H" reparte la carga: con "*/2" todos los trabajos
    // consultarian en el mismo instante; con "H" cada uno recibe
    // un desfase distinto.
    //
    // En produccion se usaria un webhook: GitHub avisa a Jenkins en
    // el momento del push, sin consultas periodicas.
    triggers {
        pollSCM("H/2 * * * *")
    }

    // ENTORNO: BUILD_NUMBER lo inyecta Jenkins. El artefacto queda
    // ligado a la ejecucion exacta que lo produjo: trazabilidad.
    environment {
        VERSION = "0.1.${BUILD_NUMBER}"
    }

    stages {

        // ETAPA 1: deja constancia de que compilador se uso.
        stage("Preparar") {
            steps {
                echo "Construyendo version ${VERSION}"
                sh "make clean"
                sh "gcc --version | head -1"
            }
        }

        // ETAPA 2 (SOURCE CODE): delega en el Makefile.
        // Si falla, el build queda ROJO y nada mas se ejecuta.
        stage("Compilar") {
            steps {
                sh "make all VERSION=${VERSION}"
            }
        }

        // ETAPA 3 (TESTING): catchError cambia el resultado a
        // UNSTABLE (AMARILLO) en vez de FAILURE (ROJO).
        //   ROJO     = no compilo, el codigo esta roto
        //   AMARILLO = compilo, pero el comportamiento no es el esperado
        stage("Probar") {
            steps {
                catchError(buildResult: "UNSTABLE",
                           stageResult: "UNSTABLE") {
                    sh "make test VERSION=${VERSION}"
                }
            }
            post {
                always {
                    // Lee el JUnit XML y lo muestra en la pestana
                    // "Test Result": cada prueba por nombre.
                    junit allowEmptyResults: true,
                          testResults: "build/reports/*.xml"
                }
            }
        }

        // ETAPA 4 (INTEGRACION): el "when" es la politica de calidad
        // automatizada. Si las pruebas dejaron el build en UNSTABLE,
        // esta etapa se OMITE.
        stage("Empaquetar") {
            when {
                expression { currentBuild.result == null ||
                             currentBuild.result == "SUCCESS" }
            }
            steps {
                sh "make package VERSION=${VERSION}"
            }
        }

        // ETAPA 5 (ENTREGA): archiveArtifacts copia el .tar.gz hacia
        // el CONTROLADOR. Por eso sobrevive al cleanWs posterior.
        stage("Entregar") {
            when {
                expression { currentBuild.result == null ||
                             currentBuild.result == "SUCCESS" }
            }
            steps {
                archiveArtifacts artifacts: "build/dist/*.tar.gz",
                                 fingerprint: true
            }
        }
    }

    // POST GLOBAL: acciones segun el resultado final.
    post {
        success  { echo "SUCCESS: artefacto ${VERSION} listo" }
        unstable { echo "UNSTABLE: compilo, pero fallaron pruebas" }
        failure  { echo "FAILURE: revise la consola" }
        always   { cleanWs() }
    }
}
Advertencia — el disparador no se activa solo

Jenkins debe leer el Jenkinsfile al menos una vez para enterarse de que existe la directiva triggers. Por eso, tras publicar el cambio es necesaria una ejecución manual; a partir de ahí el sondeo opera sin intervención.

Esto es Pipeline as Code

La elección de Pipeline script from SCM en lugar de pegar el script en el formulario web es lo que materializa el concepto: cualquier modificación del proceso de construcción llega por un commit, queda revisada y es reversible.

El cambio consiste en modificar un único carácter en src/puerta.h:

-#define MAX_INTENTOS 3u
+#define MAX_INTENTOS 2u

23:25:40  [  ok  ] test_cierre_por_tiempo
23:25:40  [ FALLA ] test_bloqueo_tras_tres_fallos
23:25:40  Resumen: 6 pruebas, 1 fallas

Este es el momento central de la demostración

La secuencia del registro cuenta la historia completa: el código compiló sin errores, pero una prueba detectó que el comportamiento ya no era el especificado. El resultado fue amarillo y no rojo, y las etapas de empaquetado y entrega se omitieron automáticamente.

Nadie tomó esa decisión: la tomó la condición when. El artefacto 0.1.2 nunca llegó a existir, y el último paquete disponible siguió siendo el 0.1.1 de la ejecución anterior.

Ejecución #3 — confirmación

Tras revertir el cambio, la ejecución #3 vuelve a verde y produce control-acceso-0.1.3.tar.gz. El ciclo completo queda demostrado: verde, amarillo, verde.

Nota — un detalle que suele confundir

El registro muestra que cleanWs() borra el espacio de trabajo después de archivar. El artefacto sobrevive porque archiveArtifacts ya lo había transferido al controlador. Esto ilustra directamente la separación entre el almacenamiento temporal del agente y la persistencia en el controlador.

Ejecución #4 — disparo automático

Nota — hasta dónde llega el ciclo

Con el disparo automático, la integración continua queda completa: cambio, detección, compilación, prueba y artefacto, sin intervención manual. La entrega continua llega hasta el paquete verificado y disponible.

El paso siguiente —desplegar al dispositivo— no se automatiza aquí, y en el dominio embebido rara vez se automatiza: no se detiene una máquina en producción para actualizarla, y un corte durante la escritura puede inutilizar el equipo.

Problemas encontrados y su solución

Los siguientes fallos ocurrieron realmente durante la construcción de esta demostración. Se documentan porque es previsible que vuelvan a presentarse.

SíntomaCausaSolución
bind source path does not exist: /usr/lib/wsl BuildKit intenta montar una ruta inexistente al crear su contenedor de construcción; ocurre con Docker Engine en WSL2 sin Docker Desktop Usar el constructor clásico: DOCKER_BUILDKIT=0 docker build -t imagen:v1 .
Password authentication is not supported GitHub no acepta contraseñas para operaciones de Git Generar un token de acceso personal y usarlo como contraseña
Permission denied ... 403 con token válido El token carece del alcance repo, o es fine-grained sin permiso de escritura Regenerar el token marcando repo, o conceder Contents: Read and write
[rejected] main -> main (fetch first) El repositorio remoto contiene commits ausentes en local, típicamente el README creado al inicializar git pull --rebase origin main y volver a publicar
Need to specify how to reconcile divergent branches Se editaron archivos desde la interfaz web mientras se trabajaba en local git config pull.rebase true y volver a integrar
stray '\' in program printf con comillas simples no interpreta secuencias de escape, de modo que quedan barras duplicadas Corregir con sed, o preferir un editor de texto para archivos con macros
missing separator en make Las reglas del Makefile requieren tabuladores reales, no espacios sed -i 's/^\t/\t/' Makefile; verificar con cat -A

Qué queda demostrado

1 · El entorno de construcción es infraestructura

La imagen de Jenkins debe extenderse para incluir el compilador; de lo contrario el pipeline no puede ejecutar make.

2 · El proceso de construcción se versiona como código

El Jenkinsfile vive en el repositorio y cada cambio queda trazable, revisable y reversible.

3 · El pipeline orquesta, no compila

Toda la lógica reside en el Makefile, de modo que lo ejecutado en el servidor se reproduce localmente sin Jenkins.

4 · No todo fallo es equivalente

Un error de compilación y una prueba fallida tienen consecuencias distintas y se distinguen visualmente.

5 · La política de calidad se aplica sin intervención humana

Un cambio de un solo carácter, sintácticamente válido, impidió que se produjera un artefacto entregable.

6 · El ciclo se cierra sin intervención humana

El sondeo del repositorio convierte un commit en una construcción verificada, sin que nadie pulse ningún botón.

Documento elaborado a partir de la construcción y verificación completa de la demostración. Todas las salidas reproducidas corresponden a ejecuciones reales.
